# Portfolio persistence design

## Entity relationship model

```mermaid
erDiagram
    PORTFOLIO ||--o{ TRADE : contains
    INSTRUMENT ||--o{ TRADE : traded_as
    INSTRUMENT ||--o{ MARKET_PRICE : has_price_history

    PORTFOLIO {
        uniqueidentifier Id PK
        nvarchar(200) Name
        char BaseCurrency
        datetimeoffset(7) CreatedAt
    }
    INSTRUMENT {
        uniqueidentifier Id PK
        nvarchar(20) Symbol
        nvarchar(200) Name
        char Currency
        int InstrumentType
    }
    TRADE {
        uniqueidentifier Id PK
        uniqueidentifier PortfolioId FK
        uniqueidentifier InstrumentId FK
        int Side
        decimal(28,10) Quantity
        decimal(28,10) UnitPrice
        datetimeoffset(7) ExecutedAt
    }
    MARKET_PRICE {
        uniqueidentifier Id PK
        uniqueidentifier InstrumentId FK
        decimal(28,10) Price
        char Currency
        datetimeoffset(7) AsOfUtc
    }
```

`Position` is calculated from a portfolio's trades and is not a persisted
entity. The required relationships are:

- One portfolio has zero or more trades; each trade references exactly one
  portfolio.
- One instrument has zero or more trades and zero or more market-price
  records; each trade and price record references exactly one instrument.
- Foreign keys use restricted deletes. Portfolios and instruments cannot be
  deleted while their trade or price history exists.

## Table mapping and constraints

| Table | Columns and SQL types | Invariants enforced by the model/database |
| --- | --- | --- |
| `Portfolios` | `Id uniqueidentifier` (PK), `Name nvarchar(200)`, `BaseCurrency char(3)`, `CreatedAt datetimeoffset(7)` | Name is non-blank and at most 200 characters; `BaseCurrency = 'USD'`; `CreatedAt` offset is zero. |
| `Instruments` | `Id uniqueidentifier` (PK), `Symbol nvarchar(20)`, `Name nvarchar(200)`, `Currency char(3)`, `InstrumentType int` | Symbol is normalized uppercase, at most 20 characters, and unique; name is non-blank and at most 200 characters; `Currency = 'USD'`; `InstrumentType = 1` (`Equity`). |
| `Trades` | `Id uniqueidentifier` (PK), `PortfolioId uniqueidentifier` (FK), `InstrumentId uniqueidentifier` (FK), `Side int`, `Quantity decimal(28,10)`, `UnitPrice decimal(28,10)`, `ExecutedAt datetimeoffset(7)` | Side is `1` (`Buy`) or `2` (`Sell`); quantity and price are positive; execution offset is zero. |
| `MarketPrices` | `Id uniqueidentifier` (PK), `InstrumentId uniqueidentifier` (FK), `Price decimal(28,10)`, `Currency char(3)`, `AsOfUtc datetimeoffset(7)` | Price is positive; currency is USD; observation offset is zero. |

IDs are generated by the application and mapped with `ValueGeneratedNever`.
The Domain constructors enforce the same supported currency, instrument type,
positive-value, and UTC rules before persistence; database checks also protect
the schema from writes that bypass those constructors.

SQL Server can round a decimal value when converting it to a fixed-scale
column. To avoid silently changing financial data, `FinCoreDbContext` checks
added or modified trades and market prices before every save. Values outside
the representable `decimal(28,10)` range (at most 18 integer digits and 10
fractional digits) are rejected before EF Core sends them to SQL Server. This
storage limit lives in Infrastructure; the provider-independent Domain
continues to validate positive decimal values without depending on SQL types.

`datetimeoffset(7)` preserves the UTC offset, while named check constraints
require that offset to be zero. `char(3)` stores the supported currency code.
Enums are stored as integers with checks for the currently supported values.
The Domain validates the same maximum string lengths as the schema:
portfolio/instrument names are limited to 200 characters and symbols to 20.
Symbols are trimmed and uppercased invariantly in the `Instrument`
constructor, and the database enforces uniqueness with
`UX_Instruments_Symbol`. This initial equity-only model does not yet include
exchange or venue identity, so the unique key is the normalized symbol alone.

## Indexes

- Primary keys are created for every entity's `Id`.
- `UX_Instruments_Symbol` is a unique index on `Instruments(Symbol)` and
  enforces one record per normalized equity symbol.
- `IX_Trades_Portfolio_Instrument_Execution` covers
  `(PortfolioId ASC, InstrumentId ASC, ExecutedAt ASC, Side ASC, Id ASC)`.
  This matches the trade repository's equality filters on portfolio/instrument
  followed by its `ExecutedAt`, `Side`, and `Id` ascending order. The prefix
  also supports serializable range locking for a specific position.
- EF Core also creates `IX_Trades_InstrumentId` for the trade-to-instrument
  foreign key.
- `IX_MarketPrices_Instrument_Latest` covers
  `(InstrumentId ASC, AsOfUtc DESC, Id DESC)`. The repository filters by
  instrument and orders by `AsOfUtc DESC, Id DESC`, allowing SQL Server to
  seek the index and return the latest price without a separate sort.

## Application and infrastructure boundaries

`FinCore.Application` defines portfolio, instrument, trade, and market-price
use cases along with `IPortfolioRepository`, `IInstrumentRepository`,
`ITradeRepository`, `IMarketPriceRepository`, and `IUnitOfWork`. These
contracts use Domain types, `Task`, and `CancellationToken`; they do not
reference EF Core.

`FinCore.Infrastructure` owns `FinCoreDbContext`, entity configurations,
SQL Server repositories, migration files, and dependency-injection
registration. Repository additions are tracked in the scoped context;
`IUnitOfWork.SaveChangesAsync` commits them. Reads are asynchronous and
no-tracking. Trade queries are ordered by execution timestamp, side, and ID.
Latest price lookup orders by observation timestamp and then ID, both
descending; as-of lookup also filters to `AsOfUtc <= requestedAsOfUtc`.
Repositories and unit of work are scoped to the same `FinCoreDbContext`.

The API reads the optional connection string through the configuration key
`ConnectionStrings:FinCore` (environment variable
`ConnectionStrings__FinCore`). No connection string or credential is stored
in tracked configuration. The EF design-time context factory reads the same
environment variable and does not print it.

## Transaction-safe trade processing

`TradeApplicationService` routes every BUY and SELL through
`IUnitOfWork.ExecuteWithExclusiveLocksAsync`. Infrastructure opens one
`SERIALIZABLE` transaction on the scoped `FinCoreDbContext` used by all
repositories, then acquires exclusive transaction-owned SQL Server
application locks before querying trade history:

- `FinCore:Trade:{tradeId:N}` serializes retries or conflicting payloads for
  the same stable caller-supplied trade GUID.
- `FinCore:Position:{portfolioId:N}:{instrumentId:N}` serializes every BUY
  and SELL affecting the same long-only position.

Distinct lock resources are sorted with ordinal comparison before acquisition.
The lock owner is the SQL transaction, so locks release on commit or rollback.
The flow reads by trade ID first for idempotency, validates parent records,
loads the complete ordered history for the affected position, validates the
candidate using the Domain position calculator, adds the trade, calls
`SaveChangesAsync`, and commits. All these operations share that transaction
and context. No schema change is required: `Trades.Id` is already a primary
key, and the chronological trade index already supports the history query.

For two concurrent sells of 7 shares against 10 available, one transaction
acquires the position lock, validates and commits, then releases the lock.
The waiting transaction subsequently reads the committed sell, calculates
only 3 shares available, and fails Domain validation. It does not insert or
commit. This serializes buys too, so no buy can race the same position
validation.

Backdated candidates are not rejected solely for being earlier than the
latest trade. The service recalculates the entire affected history including
the candidate in established order: `ExecutedAt`, BUY before SELL, then
`Trade.Id`. It rejects any intermediate oversell. Equal timestamps follow the
same deterministic ordering.

The caller-supplied GUID is both `Trade.Id` and the idempotency key. While
holding the trade-ID lock, an exact canonical payload replay returns the
stored trade without inserting again. Same ID with different portfolio,
instrument, side, quantity, unit price, or execution timestamp raises an
explicit conflict. The database primary key remains the final uniqueness
guard. Decimal comparisons treat equivalent decimal scales as equal; entity
construction requires offset-zero UTC timestamps.

Application-lock timeout (15 seconds) is surfaced as `TimeoutException`;
other negative lock results become
`TransactionLockAcquisitionException`. SQL Server deadlock error 1205 becomes
`TransactionDeadlockException` after rollback. Other transaction failures
propagate; rollback failures are reported with the original exception.
Cancellation flows to lock commands and repository/save/commit operations.
The infrastructure translates cancellation reported by SqlClient during a
lock command to `OperationCanceledException`, then attempts rollback with a
non-cancelable token. Transaction disposal is the final rollback safeguard.
No automatic retry hides failures; a caller retry after an uncertain commit
uses the same trade ID and receives either the stored result or a new attempt.

## Portfolio valuation queries and consistency

`PortfolioValuationApplicationService` uses repository contracts to read the
portfolio, its trades with `ExecutedAt <= asOfUtc`, all instruments held at
that cutoff, and each held instrument's latest market price with
`AsOfUtc <= asOfUtc`. The effective cutoff is captured once per request:
either the validated caller-supplied UTC value or
`TimeProvider.GetUtcNow()`. The existing trade and market-price indexes
support these filters and orderings; valuation introduces no table, column,
index, or migration changes.

Instrument and price repository methods query IDs in bounded batches of at
most 2,000 values, below SQL Server's 2,100-parameter limit. The price query
groups eligible rows by instrument and selects `AsOfUtc DESC, Id DESC`, so
each instrument receives one latest price and an equal-time tie resolves to
the greatest ID. Queries use `AsNoTracking` and execute sequentially on the
same scoped `FinCoreDbContext`; no concurrent operation is issued against one
EF Core context.

All valuation reads run in `IUnitOfWork.ExecuteReadOnlyInTransactionAsync`,
which uses `SERIALIZABLE` isolation and commits without `SaveChangesAsync`.
Serializable range locks make the separate trade, instrument, and price
queries observe a serializable state when records are concurrently inserted.
Those locks can block trade and price writers, increase latency, or
participate in SQL deadlocks. SQL Server error 1205 and known command
timeouts follow the existing rollback and transient-failure path; the API
returns a sanitized `503`.
Valuation does not use or alter the transaction-owned application locks used
by BUY/SELL writes.

Positions are derived from the cutoff-filtered trades using the Domain
ordering, and zero quantities are omitted. An empty set returns USD zero
without querying prices. A missing eligible price for any open holding fails
the whole operation and reports all missing instrument IDs/symbols; no
partial total is returned. The current policy does not reject stale prices:
the selected `AsOfUtc` is returned for clients to assess. Future-dated prices
are excluded by the cutoff predicate. Per-position multiplication reuses
`StockValuationService`; the portfolio sum is checked decimal arithmetic
with no rounding. Overflow is a `422` response rather than a partial or
truncated value.

## Migration and database status

The `20261115200739_InitialPortfolioPersistence` migration and model snapshot
are in
[`src/FinCore.Infrastructure/Persistence/Migrations`](../src/FinCore.Infrastructure/Persistence/Migrations/).
The migration has been applied to the local `FinCore` development database.
SQL Server verification confirmed the four application tables and the
`__EFMigrationsHistory` entry. The live column types and lengths, indexes and
key order, foreign keys with `NO_ACTION` delete behavior, and all 11 check
constraints match the migration and EF model. In particular,
`UX_Instruments_Symbol` is unique;
`IX_Trades_Portfolio_Instrument_Execution` orders keys as
`PortfolioId ASC, InstrumentId ASC, ExecutedAt ASC, Side ASC, Id ASC`; and
`IX_MarketPrices_Instrument_Latest` orders keys as
`InstrumentId ASC, AsOfUtc DESC, Id DESC`.

SQL Server integration tests are opt-in and use the existing
`FINCORE_SQLSERVER_TEST_CONNECTION_STRING` only as a credential/configuration
source. The fixture requires its catalog to be exactly
`FinCoreIntegrationTests` but never opens that database. It rewrites the
catalog to `master`, checks the endpoint is local loopback port 1433, and
verifies SQL Server 2022 Developer Edition and sysadmin permission before
creating or dropping databases.

On Windows with the Compose IPv4-only port binding, the test connection must
use `127.0.0.1,1433` rather than `localhost,1433`. Windows resolves
`localhost` to `::1` before `127.0.0.1`; Microsoft.Data.SqlClient can time out
connecting to the unpublished IPv6 endpoint before SQL Server receives a
pre-login request. Explicit IPv4 avoids this address-selection failure without
changing encryption, certificate validation settings, timeout, or pooling.

Each test collection fixture generates a new `FinCoreTestRun_<GUID>` name,
refuses to reuse an existing name, creates that exact database, writes a
database-level extended-property ownership marker containing the run ID, and
applies migrations with `MigrateAsync`. Tests sharing a fixture are
serialized; parallel test runs receive different GUIDs. Cleanup revalidates
the exact generated name and ownership marker immediately before dropping
only that fixture's database. If the marker or local server validation fails,
cleanup refuses the drop and reports an error. It never uses broad database
name matching for a destructive operation.

Migration verification asserts the expected `__EFMigrationsHistory` row,
three foreign keys with restricted (`NO_ACTION`) deletes, all 11 check
constraints, index uniqueness and ordered key columns, and duplicate-symbol
rejection after Domain normalization. A raw SQL check also confirms that
database check constraints reject invalid currency and non-positive prices.
Neither `FinCore` nor the existing `FinCoreIntegrationTests` database is
modified, reset, or dropped by this fixture.

The previous persistent `FinCoreIntegrationTests` database was created using
`EnsureCreated` and was verified to have no migration-history table or unique
symbol index. `EnsureCreated` does not apply or update migrations for an
existing schema; it is no longer used by the integration tests.

## Application transaction verification

The Prompt 5A SQL tests use the same fixture and migration process; they do not
change the migration or DbContext model. Two consecutive runs each passed all
14 SQL Server integration tests with 0 failures and 0 skips. Coverage includes
two simultaneous 7-share sells against a 10-share holding (one commits, one
is rejected), valid and invalid backdated trades, equal execution timestamps,
identical replay and conflicting payloads, rollback followed by retry with
the same trade ID, cancellation while waiting for an application lock, and
the 15-second lock timeout.

The complete solution test run passed all 54 unit tests; its 14 SQL tests were
skipped because the opt-in connection variable was absent. The build had 0
warnings and 0 errors, `git diff --check` passed, and the solution vulnerability
audit found no vulnerable packages. A read-only post-run check found no
remaining `FinCoreTestRun_` databases. `FinCore` still had 0 rows in its four
application tables; `FinCoreIntegrationTests` still contained 3 portfolios,
6 instruments, 3 trades, and 9 market prices. Neither database was used as a
test target or modified.

## Portfolio valuation verification

The valuation additions use the existing schema, migration, and indexes.
The complete solution test run passed 78 unit/in-memory HTTP tests and skipped
20 opt-in SQL tests, with 0 failures. Two independent SQL integration runs
each passed all 20 tests with 0 failures and 0 skips; every run used and
cleaned its own fixture-generated database. Valuation coverage verified
historical trade/price cutoffs, greatest-ID tie-breaking for equal price
timestamps, and a valuation concurrent with an atomic trade-and-price update.
The SQL-backed HTTP end-to-end test verified a 100-share buy, 20-share sale,
and USD 450 simulated price result in 80 shares and USD 36,000 total value.
The solution build completed with 0 warnings and 0 errors, the vulnerability
audit reported no vulnerable packages, and `git diff --check` was clean.

The later publication-audit follow-up added a long-symbol stock-pricing
regression test without changing the registered-instrument `nvarchar(20)`
column or its validation. Its solution run passed 79 unit/in-memory HTTP
tests and the fixture endpoint guardrail test, and skipped the 20 opt-in SQL
tests. Two subsequent isolated SQL runs passed all 20 tests each, with no
failures or skips. Protected database row counts remained unchanged and no
run-owned database remained. The local Windows fixture requires
`127.0.0.1,1433` because the Compose port is IPv4-only.

The new valuation transaction is read-only: repository queries are
no-tracking and sequential, and
`IUnitOfWork.ExecuteReadOnlyInTransactionAsync` commits without calling
`SaveChangesAsync`. It uses `SERIALIZABLE` range locking for a consistent
multi-query read. The fixture still targets only `FinCoreTestRun_<GUID>`
databases; it does not target or modify `FinCore` or
`FinCoreIntegrationTests`, and it does not delete Docker volumes.
